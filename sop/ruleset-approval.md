# SOP: 룰셋(배출계수·규제 룰) 승인 절차

**대상 독자:** CarbonGuard 운영자(창업자/변호사). 개발 지식이 없어도 따라할
수 있도록 작성했습니다.

## 왜 이 절차가 필요한가

배출계수나 CBAM/CCA/CSRD 규제 수치가 틀리면 고객사의 세금·보고 의무에
직접적인 금전적/법적 영향을 줍니다. 그래서 AI가 이 값을 **혼자 추측해서
채우거나 바꾸는 것을 시스템 차원에서 막아두었습니다.** 값이 바뀌려면 반드시
이 절차를 거쳐야 합니다.

## 절차

1. **제안 확인**: `packages/ruleset/proposals/` 폴더에 새 파일이 있는지
   확인합니다. reg-watcher가 매주(또는 수동 실행 시) 원문 소스 변경을
   감지하면 여기에 파일을 만들어 둡니다.
2. **원문 직접 확인**: 제안 파일에 적힌 출처 URL을 **반드시 직접 열어서**
   확인합니다. AI가 요약한 내용만 믿지 마세요 — 특히 세율, 발효일 같은
   숫자는 원문에서 직접 캡처하거나 인용하세요.
3. **값 반영**: 실제로 반영할 값이 확인되면
   - `packages/ruleset/factors/...` 또는 `packages/ruleset/regulations/...`
     파일을 직접 엽니다.
   - `TODO`로 되어 있던 필드를 확인한 값으로 바꿉니다.
   - `source` 필드에 원문 URL을 넣습니다.
4. **changelog 기록**: `packages/ruleset/changelog.md`에 아래 형식으로
   한 항목을 추가합니다 (이 기록이 없으면 시스템이 커밋 자체를 막습니다).
   ```
   ## YYYY-MM-DD — packages/ruleset/<경로>
   - 작성자: <이름>
   - 근거 URL: <원문 URL>
   - 변경 요약: <무엇이 왜 바뀌었는지>
   ```
5. **제안 파일 정리**: `packages/ruleset/proposals/`에서 처리 완료된
   제안 파일을 삭제합니다.
6. **승인 대기열 정리**: 만약 이 변경이 이미 사용 중인 리포트에 영향을 준다면,
   앱의 승인 대기열(approvals)에서 관련 항목도 함께 검토합니다.

## 절대 하지 말아야 할 것

- 원문을 확인하지 않고 AI 요약만 보고 값을 반영하는 것
- changelog 기록 없이 factors/regulations 파일을 고치는 것
- "일단 비슷한 값으로 채워두자"는 식의 임시 수치 입력 — 확실하지 않으면
  `TODO`로 남겨두는 편이 항상 낫습니다.
