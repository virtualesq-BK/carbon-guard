# SOP: 장애 대응 절차

**대상 독자:** CarbonGuard 운영자. "뭔가 잘못된 것 같다"는 신호를 받았을 때
읽습니다.

## 1. 잘못된 배출계수/규제 값이 이미 반영되어 리포트가 나간 경우

1. 즉시 해당 factor/regulation 파일을 정확한 값으로 수정하고,
   `changelog.md`에 "정정" 항목을 추가합니다 (원래 항목을 지우지 말고
   새 항목으로 추가 — 이력을 남기기 위함).
2. 영향받은 `reports`를 조회합니다 (`content`에 해당 `factor_ref`를
   사용한 것들).
3. 고객사에 정정 사실을 알릴지 판단합니다. **규제기관에 이미 제출된
   리포트(`status: submitted`)라면 법적 정정 절차가 필요할 수 있으니
   변호사(운영자 본인 또는 자문) 검토를 최우선으로 합니다.**
4. `agent_logs`와 `logs/`를 확인해 언제, 어떤 값으로 계산이 이뤄졌는지
   재구성합니다 — emission-engine은 결정론적이므로 같은 입력이면 같은
   출력이 나온다는 점을 활용해 영향 범위를 정확히 특정할 수 있습니다.

## 2. 에이전트가 승인 없이 무언가를 반영한 것 같은 경우

이 시스템은 구조적으로 이런 일이 일어나지 않도록 설계되어 있습니다
(ruleset 쓰기는 하네스 훅으로 차단, 리포트 발행은 approvals 게이트 필수).
만약 발생했다면:

1. 즉시 관련 API 키(ANTHROPIC_API_KEY, SUPABASE_SERVICE_ROLE_KEY)를
   교체하는 것을 고려합니다.
2. `agents/*/CLAUDE.md`와 `.claude/settings.json`의 hooks 설정이
   실제로 로드되고 있는지 확인합니다.
3. `logs/`에서 해당 시점의 로그를 찾아 어떤 에이전트가 무엇을 했는지
   확인합니다.
4. 근본 원인을 고친 뒤, 이 문서와 root `CLAUDE.md`에 재발 방지 항목을
   추가합니다.

## 3. reg-watcher가 며칠째 조용한 경우 (스케줄 실패 의심)

1. GitHub Actions(설정되어 있다면) 실행 이력을 확인합니다.
2. `agents/reg-watcher/state/`의 각 소스별 `lastCheckedAt`을 확인해
   마지막 조회 시각을 파악합니다.
3. 수동으로 `pnpm agent:reg-watch`를 실행해 즉시 재조회합니다.

## 4. 데이터베이스/서비스 장애

1. Supabase 대시보드에서 장애 상태를 확인합니다.
2. 장애 중 들어온 고지서 업로드/리포트 요청은 큐에 남아있는지, 유실됐는지
   확인합니다 (현재 설계는 재시도 큐가 없으므로 유실 가능성을 염두에 두고
   고객에게 재업로드를 안내할 수 있습니다).
3. 복구 후 `agent_logs`에 빈 시간대가 있는지 확인해 유실된 처리를
   식별합니다.
